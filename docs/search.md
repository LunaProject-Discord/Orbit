# メールの検索の仕組み

検索欄の書き方と画面の動きは README の「検索」を参照。ここではサーバー側の仕組みをまとめる。

## 検索用の文字列 (`message_search`)

- メール 1 通に 1 行。`doc` は、件名・差出人・宛先 (To / Cc / Bcc)・本文を、それぞれ `mail_search_normalize` で
  そろえてから制御文字 `\x01` でつないだもの (`件名 \x01 差出人 \x01 宛先 \x01 本文`)。
- `mail_search_normalize` は NFKC (全角英数・半角カナなどをそろえる) → 小文字 → 空白・ゼロ幅文字・制御文字を除く。
  API と Web の `foldForSearch` (`search-fold.ts`) は同じそろえ方の写しで、目立たせる位置や抜粋、オフラインの検索に使う。
  変えるときは 3 か所をそろえること。
- 本文は、テキストがあればテキスト、無ければ HTML からタグ・スタイル・スクリプトを除いて文字参照を戻したもの
  (`mail_search_html_text`)、本文の取得前は冒頭の抜粋。
- `messages` への追加と、件名・宛先・本文などの変更のたびに、トリガー (`messages_search_sync`) が作り直す。
  既読などの変更では作り直さない。

## 索引 (`message_search_grams_idx`)

- `mail_search_grams(doc)` (1 文字ずつと、隣り合う 2 文字の組) の GIN 索引。拡張は使わない
  (pg_trgm は 3 文字の組なので、1〜2 文字の語では索引が効かなかった)。
- 語 (そろえたもの) が 1 文字ならその文字、2 文字以上なら隣り合う 2 文字の組 (`mail_search_query_grams`) で候補を引く。
  場所を限定しない 2 文字以下の語はこれで決まり、それ以外は `LIKE` (場所を限定するときは `split_part(doc, chr(1), n)`) で確かめる。
- よく出る語では、索引の語だけで新しい順に候補を取り、候補を 1 通ずつ確かめる (`routes/search.ts`)。
  確かめて残る割合が低い (語が離れて現れるだけのメールが多い) ときは、続きを索引と `LIKE` で探す。
- 索引で引くのは DB の関数 `mail_search_ids` (マイグレーション 0046) に任せる。副問い合わせに直接書くと、
  よく出る文字 (「a」や英語の「ca」「re」など) の語で DB が表を順に読み、1 通ずつ `mail_search_grams` を計算する計画を選ぶことがあった
  (1 通 約 1 ミリ秒で、10 万通では 30 秒以上)。関数に `SET enable_seqscan = off` を付けて、関数の中だけ必ず索引を使わせている。

## 更新した直後 (マイグレーション 0037)

- マイグレーションは、関数・表・トリガーを作り、以前の検索用の生成列と pg_trgm の索引を外すだけで、
  全件の書き換えも索引作りもしない (メールが多くても数秒で終わる)。
- 同期ワーカーが起動時に、行の無いメールの分を 1,000 通ずつ作り、そろったら `CREATE INDEX CONCURRENTLY` で索引を作る
  (`apps/worker/src/search-index.ts`。メールの読み書きは止めない)。ログに「検索の索引を作りました」と出れば完了。
  途中で止まっても、次の起動で続きから作る (作りかけの索引は作り直す。別の接続が作っている途中なら、終わるのを待つ)。
- API は、索引が有効ですべてのメールに行がそろうまで、索引を使わずに探す (結果は同じだが遅い)。そろったかは 30 秒ごとに確かめる。
- 計測 (疑似的な日本語メール 9.8 万通、x86 4 コアのクラウド環境): 行の作成 約 30 秒、索引の作成 約 4 分、索引の大きさ 約 230 MB。
  以前の 4 つの trigram 索引 (本文だけで約 360 MB) は外れる。
